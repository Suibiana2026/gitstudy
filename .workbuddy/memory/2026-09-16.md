## ⚠️ 已定位的 BUG：HDFS FileSystem 被 close，导致「采集成功但数据没进 HDFS」

（用户反馈「采集不了数据了」，已诊断，**尚未修复** —— 用户要求先只给原因。）

### 现象
- `POST /WebSocket/collect/tcp` 返回 `status: success`、`filePath=/original_data/xxx.csv`，前端显示成功。
- 但 `GET /HDFS/ListOriginalDataFiles` 返回 **HTTP 500 `Server error: Filesystem closed`**；
  `/HDFS/previewOriginalData/...` 也是 500。
- 用 WebHDFS 直查确认：刚"采集成功"的文件 `HTTP 404`，**根本没写进 HDFS**。
  `/original_data` 里最新的文件还是 09-15 的，今天(09-16)一个都没落。

### 根因（两层）
1. **共享 FileSystem 单例被 close**
   - `Config/HadoopConfig.fileSystem()` 用 `FileSystem.get(conf)` 创建 Bean。
     Hadoop 的 `FileSystem.get()` 返回的是**按 (scheme, authority, user) 缓存的单例**。
   - 任何同样用 `FileSystem.get(conf)` 拿实例、又把它关掉的地方，都会**关掉这个共享 Bean**。
     全项目命中：
     - `service/Agent/AgentTools.java:174,187`（`closeQuietly(fs)`）← **今天新加的代码，最大嫌疑**
     - `controller/WebSocket/DataCollectionController.java:68`（try-with-resources，「模拟采集」按钮）
     - `controller/HDFS/DownloadAllFiles.java:41`（try-with-resources）
     - `service/HDFS/UploadService.java:52`（`fs.close()`）
   - 关闭后，`FileLists1` 等**构造函数注入 FileSystem 的 Controller 一直握着那个已死的引用**，
     所以永远抛 `Filesystem closed`（注意：`FileSystem.get()` 再次调用会新建实例，
     这解释了为什么采集通道还能跑、列表却必挂）。
2. **`Server.uploadFileToHDFS` 假成功**
   - `Server.java:224-239`：`catch (IOException e) { logger.error(...) }` **吞掉异常**，
     然后**无论如何都 return target**。所以 HDFS 写失败也照样对外报 success。

### 触发点
09-15 的文件都在，说明昨天正常；今天坏掉 —— 与今天用智能体页有关
（点「原始数据文件」等卡片会走 `AgentTools.listHdfsFiles` → 关掉共享 FS）。
但注意第 2、4 条是历史遗留写法，`模拟采集` 按钮同样会触发。

### 修复方向（待用户确认后再做）
- `AgentTools` 改为不关共享实例（去掉 `closeQuietly`），或复用注入的 `FileSystem` Bean；
- 顺手把 `DataCollectionController` / `DownloadAllFiles` / `UploadService` 的同类写法一并收口；
- `Server.uploadFileToHDFS` 改为向上抛出/返回失败标记，避免假成功；
- 彻底方案：`HadoopConfig` 用 `fs.close()` 的替代或改为每次 `FileSystem.newInstance()`。

### ✅ 已修复（2026-09-16 11:1x）

**核心手法：所有会 close 的地方一律 `FileSystem.get()` → `FileSystem.newInstance()`。**
`get()` 返回全局缓存单例，`newInstance()` 带唯一键创建独立实例，谁 close 只影响自己。

| 文件 | 改动 |
|---|---|
| `Config/HadoopConfig.java` | Bean 改用 `newInstance` —— 注入该 Bean 的 `FileLists1`/`PreviewFile1`/`Server` 从此免疫 |
| `service/Agent/AgentTools.java` | `openFileSystem()` 改 `newInstance`（**本次故障的元凶**） |
| `service/HDFS/UploadService.java` | init 改用 `newInstance`（它 @PreDestroy 会 close） |
| `controller/WebSocket/DataCollectionController.java` | simulate 的 try-with-resources 改 `newInstance` |
| `controller/HDFS/DownloadAllFiles.java` | 同上 |
| `controller/HDFS/ProcessedData/` 的 FileLists2 / PreviewFile2 / DeleteFile2 / DownloadFile2 | 同上（4 个文件） |
| `service/API/Server.java` | `uploadFileToHDFS` 失败返回 `null` 不再返回路径；record 增加 `uploadSuccess` 字段 |
| `controller/WebSocket/DataCollectionController.java` | `collectByTcp` 检测 `uploadSuccess=false` 时返回 500 + 真实原因，杜绝假成功 |

未改动的 `FileSystem.get()` 站点（`DataCleaningController`×3、`UploadFileController`、`MapReduceServiceImpl`×2）
都是**只取不关**，安全，故保持最小改动。

编译 BUILD SUCCESS。**仍需重启应用**（进程里那个已死的 Bean 不会自愈）。

- **项目里没有任何代码/SQL 往 `basic_info`、`parcel_rank`、`platform_proportion`、`monthly_statistics`
  写数据**（全项目搜 insert/seed 无结果；`repository.save` 只有聊天记录）。
  这几张表是**手工塞的**（建库时在客户端里插的），属原始模板数据 —— 答辩若被追问「数据哪来的」是风险点。
- **唯一会被程序改写的**是 `automobile_brand_sales_ranking`：`StatisticsImportService` 用原生 JDBC
  （DELETE + INSERT brand_name/sales）写入。入口两个：数据清洗页「统计入库」按钮，以及我新加的智能体工具
  `import_statistics_to_db`。即：**「统计入库到大屏」是全项目唯一打通「操作 → 大屏」的链路。



- `mvn -o -q compile` 后静态资源同步到 target/classes，**无需重启即生效**（已用 curl 验证页面含新内容）。
